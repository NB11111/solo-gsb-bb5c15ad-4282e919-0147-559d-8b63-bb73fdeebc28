# 匿名评审分配系统（Review Assignment · MCMF）

基于 **Python + FastAPI + SQLite + 原生 HTML/CSS/JS** 的单容器 Web 应用。
用**最小费用最大流（Min-Cost Max-Flow）**为稿件分配评审人：

- ✅ **冲突边绝不使用**——作者冲突的“稿件–评审人”边根本不会加入流网络；
- ⚖️ 费用同时惩罚 **主题不匹配**（β × 未覆盖主题数）与 **评审负载偏差**（凸增边际成本 α·k，天然均衡）；
- 🔒 允许**锁定少量既有分配后重新求解**，锁定边预占稿件名额、评审容量与**机构名额**并参与负载计费；
- 🏛️ **机构多样性硬约束**：评审人可填写可选机构，可配置“每篇稿件同机构最多人数”（0 为关闭）；未填写机构者不计入该上限；历史锁定已超限时保留锁定、发出警告且不再向该稿该机构分配新人，新增锁定会超限时接口返回 **409**；
- 👑 **主审资格硬约束**：评审人可标记“**可任主审**”，每篇稿件可设置**需主审人数 0～2**（且不得超过所需评审总数，0=不要求）。主审与普通评审一样同时占用**稿件需求、个人容量与机构名额**，同一人对同一稿至多分配一次；合资格的**有效锁定按评审人 ID 顺序优先抵扣主审名额**，不足部分由自由分配补齐；主审不足时仍返回**最大可行分配**，但把该稿列入未满足并分别给出**主审缺口与总人数缺口**；
- ⛔ 容量/主审不足时给出**未满足稿件清单**和**可复核的原因明细**（冲突排除人数、**机构上限排除人数**、主审资格、各候选评审剩余容量与主题覆盖情况、全局容量缺口）；
- 🗃️ SQLite 单文件持久化，数据卷挂载；无前端构建步骤、无第三方 JS 依赖。

## 一条命令启动

需要安装 Docker（含 Compose 插件）。在项目根目录执行：

```bash
docker compose up --build -d
```

这一条命令会完成：

1. 构建镜像并安装全部 Python 依赖（`requirements.txt`）；
2. 启动容器时**自动初始化数据库**：建表、写入默认求解参数、载入演示数据（首次启动）；
3. 在后台启动 FastAPI / uvicorn 服务。

启动后访问：

> **http://localhost:8000**

- 前端页面：<http://localhost:8000/>
- 接口总览（Swagger）：<http://localhost:8000/docs>
- 健康/状态接口：<http://localhost:8000/api/state>

停止 / 查看日志：

```bash
docker compose logs -f
docker compose down          # 停止（数据保留在卷 review-data 中）
```

不想要演示数据（空库启动）时，将 `docker-compose.yml` 中的 `SEED_DEMO` 改为 `"0"` 后重建；
或删除卷重新开始：`docker compose down -v`。

### 不使用 Docker（本地开发）

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

数据库默认创建在 `./data/review.db`（可用环境变量 `DB_PATH` 覆盖），首次启动自动建库并写入演示数据。

冒烟测试（仅标准库）：

```bash
python -m tests.test_smoke
```

## 使用说明

页面共 4 个标签页：

| 标签页 | 功能 |
| --- | --- |
| **分配结果** | 一键“重新求解分配”；查看每篇稿件的评审人、**实际主审（👑）**、**机构构成**、费用拆解、评审人负载条（含主审资格标识）；🔒 锁定/解锁既有分配；展开未满足稿件的原因明细（区分主审缺口与总人数缺口）；调整求解权重、机构上限与默认值 |
| **稿件** | 录入稿件主题（逗号/顿号分隔）、设置**每稿所需评审数**与**需主审人数（0～2）**；编辑、删除 |
| **评审人** | 录入评审人擅长主题、**可选所属机构**、**个人容量**与**“可任主审”资格**；编辑、删除 |
| **作者冲突** | 用勾选矩阵登记“稿件–评审人”冲突；已锁定的分配需先解锁才能登记冲突 |

顶部按钮：

- **▶ 重新求解分配**：按当前数据与权重运行 MCMF，生成完整分配；
- **载入演示数据**：恢复内置示例（含一个刻意制造的容量不足样例）；
- **清空全部**：删除所有稿件、评审人、冲突与分配。

> 锁定任意分配后系统会**立即自动重新求解**；无需再点“重新求解”。

## 优化模型

### 网络结构

```
   cap=尚缺主审数        cap=1            凸增单位槽位
S ───────────────► C_i ───────────────► R_j ───────────────► T
  │  (主审通道;只接       （仅“可任主审”且无冲突、未锁定的评审人）  cost = α·k
  │   合资格评审人边)           │
  │                     [机构: C_i→P^c→Q→R_j]
  │
  │ cap=need-chair_need        cap=1（边费 +δ）
  └───────────────► N_i ───────────────► R_j ───────────────► T
     （普通通道；所有非冲突、未锁定评审人）

回流边 C_i ──(cap=chair_need, cost=2δ)──► N_i
   （合资格主审实在不足时，主审通道余量转为普通名额，以最大化总分配数）

机构路径（γ>0 且评审人填有机构 a 时）：
   C_i ─► P^c_{i,a} ─┐
                     ├─► Q_{i,a}（Q→U 唯一配额边, cap=γ−锁定数）─► U_{i,a} ─► R_j
   N_i ─► P^n_{i,a} ─┘
```

- **S → 主审通道 C_i**：容量 = 该稿尚缺的主审数（主审需求扣除已锁定主审），只连接**具备“可任主审”资格**的评审人；
- **S → 普通通道 N_i**：容量 = 尚缺总名额 − 尚缺主审数；两条通道汇入**同一组**“每对容量 1”的
  分配边与**同一组**评审人负载槽位，因此同一评审对同一稿件至多 1 次、总分配数不超过需求，
  且主审与普通评审共享**个人容量**与**机构名额**；
- **主审优先惩罚 δ**：普通通道分配边在主题费之外加收 δ（δ 大于任意单位流的原始费用上界），
  主审通道不收。于是在“**最大可行分配**优先”（最大流）的前提下，算法总是优先用合资格者补齐主审名额；
  当合资格主审确实不足时，回流边 `C_i→N_i`（费用 2δ）把主审通道余量转为普通名额，总人数仍最大化，
  该稿则带着**主审缺口**进入未满足清单。δ/2δ 仅为算法优先级，输出费用会全额扣除（见下“费用口径”）；
- **稿件 → 评审人**：容量 1（同一评审对同一稿件至多评审一次）；
  **冲突边与已锁定边不会被创建**，因此从结构上保证绝不使用；
  费用 = `β ×（稿件主题 − 评审擅长主题）的数量`；
- **机构多样性（硬性）**：当 `institution_cap = γ > 0` 且评审人填有机构 a 时，
  两条通道分别进入匹配节点 `P^c/P^n`，再汇入唯一的配额边 `Q_{i,a} → U_{i,a}`
  （容量 = `γ − 该稿来自 a 的锁定数`）。主审通道与普通通道**共享同一配额**，
  故主审同样占用机构名额；名额被锁定占满（或历史锁定已超 γ）时配额边不建立，
  从而本稿绝不会再被分到该机构的人。**未填写机构的评审人走直接边，不占用、也不受机构名额限制。**
- **评审人 → T**：容量拆为单位“负载槽位”，第 k 个槽位费用 `α·k`（k 从该评审锁定数之后连续计）。
  边际成本递增使流算法自动偏好更空闲的评审人——这就是“负载偏差”惩罚。

### 主审资格硬约束

- 评审人字段 **`can_chair`（可任主审）**：仅勾选者可出任主审；稿件字段
  **`required_chairs`（需主审人数）**：取值 **0～2**，创建/更新时校验
  **不得超过 `required_reviews`**（接口入参非法返回 422/400）；`required_chairs = 0` 即该稿不要求主审；
- 主审与普通评审占用完全相同的三类资源：**稿件名额、评审个人容量、每稿机构名额**，
  且“同一人对同稿只能分配一次”；
- **锁定优先抵扣**：每篇稿件的有效锁定（对象存在、无冲突、未超需求）按**评审人 ID 升序**选取，
  其中具主审资格者依次抵扣该稿主审名额；被选为主审的锁定在结果中标记 `is_chair`；
  锁了不具资格的人不抵扣主审名额，主审改由自由分配补齐；
- **主审不足时**：不牺牲总分配数——仍返回最大可行分配，但把该稿列入 `unmet`，
  同时返回 `chair_deficit`（主审缺口）与 `deficit`（总人数缺口，可能为 0）；
  `solution.total_chairs_required / total_chairs_assigned` 给出全局主审统计，
  `solution.chairs` 给出每稿实际主审的评审人 ID；
- **候选明细** `details.candidates[]` 对每位非冲突候选给出：
  `can_chair`（资格）、`chair_available`（资格+容量+机构是否当前可补主审）、
  `chair_block_reason`（`not_qualified` 无资格 / `no_capacity` 容量不足 / `institution` 机构阻断），
  以及剩余容量、主题匹配、`blocked_by_institution`，可逐项人工复核。

#### 费用口径

主审优先惩罚 δ 只是流网络中的次序工具：`solution.free_cost / total_cost` 与各边
`edge_costs` 中展示的费用均已扣除 δ 与回流边 2δ，**与“未启用主审约束”时的费用口径完全一致**
（总费用恒等于全部已分配边 `mismatch_cost + load_cost` 之和）；主审不额外收费。

### 机构多样性约束

- 评审人的机构为**可选**自由文本；空（未填写）表示独立、不计入任何机构上限；
- 设置 `institution_cap`（每篇稿件同机构最多人数）：`0` 为关闭，`≥1` 时与冲突、容量同级作为**硬约束**；
- 锁定先占用机构名额；若历史锁定本身已超过 γ（例如上限调小或导入存量数据）：
  **锁定强制保留**、求解警告逐条列出（`institution_lock_over_cap`），本次不再向该稿该机构安排新人；
- 通过接口新增一把锁会使该稿同机构人数超过 γ 时，`POST /api/assignments/lock` 返回 **409**，
  请先解锁一名该机构的锁定或放宽上限（把已有自由分配转为锁定不增加人数，故不拒绝）；
- 分配结果中每篇稿件返回 `solution.institutions`（机构、人数、其中锁定数、是否超限）。

### 锁定的既有分配

锁定边不进入网络，而是：

1. 预占该稿件一个名额（S→通道容量减 1）；
2. 预占该评审一个容量槽位（自由槽位减少，锁定数超过容量时自由容量为 0，并给出告警）；
3. 预占一个**机构名额**（M→机构节点容量减 1；历史锁定超机构上限时见上）；
4. **合资格锁定按评审人 ID 升序优先抵扣主审名额**（不具资格者不抵扣）；
5. 按相同规则计入总费用（主题费 + 其所处槽位的负载费），保证锁定与新求解目标口径一致。

非法锁定（指向已删除对象、与冲突边重合、超过稿件需求）会被跳过并在“求解警告”中逐条列出，**不会静默处理**。

### 容量/主审不足时的输出

最大流流量小于总需求、或某稿主审未补齐时，对每篇未满足稿件返回：

- `required / assigned / deficit`（总人数口径）与
  `required_chairs / assigned_chairs / chair_deficit`（主审口径，两者分别给出）；
- 自然语言原因（冲突排除人数、**机构上限排除人数**、主审资格/容量/机构阻断、
  候选剩余总容量、是否全局容量不足等）；
- `details.candidates`：每位**非冲突且未已分配**评审人的主审资格（`can_chair`）、
  是否可补主审（`chair_available`、`chair_block_reason`）、剩余容量、未覆盖主题数，
  以及 `blocked_by_institution`（是否被机构上限硬性排除），可人工逐项复核。

### 可调参数（页面“求解参数与默认值”）

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `mismatch_weight` (β) | 10 | 每个未覆盖稿件主题的费用 |
| `load_weight` (α) | 2 | 第 k 个负载槽位费用系数（越大负载越均衡；设 0 关闭负载惩罚） |
| `institution_cap` (γ) | 0（演示数据为 2） | 每篇稿件同机构最多人数；**0 关闭机构多样性约束**，未填机构者不计入 |
| `default_required_reviews` | 3 | 新建稿件的默认所需评审数 |
| `default_capacity` | 3 | 新建评审人的默认个人容量 |

MCMF 实现见 `app/mcmf.py`（SPFA + Successive Shortest Path，可正确处理残量网络中的负权反向边），
业务建模见 `app/solver.py`。

## REST API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 一次性拉取全部数据（稿件/评审人/冲突/分配/上次解） |
| POST / PATCH / DELETE | `/api/manuscripts[/{id}]` | 稿件增改删（含 `required_chairs` 需主审人数 0~2，且 ≤ 所需评审数） |
| POST / PATCH / DELETE | `/api/reviewers[/{id}]` | 评审人增改删（含可选 `institution` 与布尔 `can_chair` 可任主审） |
| POST / DELETE | `/api/conflicts`、`/api/conflicts/{m_id}/{r_id}` | 冲突登记/移除 |
| PUT | `/api/settings` | 权重、`institution_cap` 与默认值 |
| POST | `/api/solve` | 运行 MCMF 求解 |
| POST | `/api/assignments/lock` | 锁定/解锁并立即重新求解；**新增锁定会使同机构人数超过上限时返回 409** |
| POST | `/api/demo`、`/api/reset` | 载入演示数据 / 清空 |

所有写接口均返回最新的完整状态，前端无需二次拉取。

## 数据持久化与版本迁移

- Docker：SQLite 文件位于容器内 `/data/review.db`，映射到命名卷 `review-data`；
- 本地：默认 `./data/review.db`（已加入 `.gitignore`）。
- **保留既有数据**：应用启动时执行幂等迁移，旧版本数据库会自动
  `ALTER TABLE reviewers ADD COLUMN institution TEXT NOT NULL DEFAULT ''`、
  `ALTER TABLE reviewers ADD COLUMN can_chair INTEGER NOT NULL DEFAULT 0`、
  `ALTER TABLE manuscripts ADD COLUMN required_chairs INTEGER NOT NULL DEFAULT 0`，
  并补入新设置项 `institution_cap = 0`（默认关闭，升级后行为与旧版本一致）。
  其中旧评审默认**不具主审资格**、旧稿件默认 **`required_chairs = 0`（不要求主审）**，
  即主审硬约束对历史数据默认关闭，需要时在页面勾选/设置即可；
  `docker compose up --build` 升级无需手动操作，卷中历史数据、锁定均保留。
